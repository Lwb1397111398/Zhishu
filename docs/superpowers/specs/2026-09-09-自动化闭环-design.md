# 设计:打通生成流程的自动化闭环

日期:2026-09-09
状态:已确认,待实施

## 问题

当前应用("知书"知识学习小说工具)的生成流程没有闭环,三处实证:

1. **"继续"不自动推进。** 一键开讲只排「知识主干 → 讲述路线 → 一章」(`GenerationEnqueuer.kt:156-190`),跑完即停;第 2 章起每章都要再点一次「生成未完成」。链中任何一环失败,WorkManager 不再执行链尾(`GenerationWorker.kt:151-156`),后续全靠手动。
2. **核验与漏知识点在自动化之外。** 审计产出的 gap 只能逐条手点 `generateKnowledgeMapPatch`(`PipelineService.kt:715`);`planNextVolume` 只存在于 VM 按钮回调(`ZhishuViewModels.kt:690`),没有任何 Worker 路径会调它。
3. **用户永远只见第一卷。** 根因两条:
   - 卷门:`nextVolumeAvailability` 要求当前卷全部 `isReadable`(`PipelineService.kt:1574-1583`),而 `isReadable = PUBLISHED || QUIZ_FAILED`(`Chapter.kt:34`)不含 NEEDS_REVIEW——任何一章停在待复核,"继续下一卷"按钮就永久不出现(`ProjectDetailScreen.kt:1808-1814`)。
   - 即使点亮按钮,`generateNextVolume` 只写 QUEUED 计划就返回(`PipelineService.kt:1689-1701`),还要再点一次「生成未完成」。两连击缺一,就没有第二卷。

## 已确认的产品决定

| 决定点 | 结论 |
|---|---|
| 自动化边界 | **全链自动**:点一次「继续」→ 逐章生成 → 卷末自动续卷 → 继续生成,直到刹车 |
| 待复核(NEEDS_REVIEW) | **带问题继续跑**:链不为它断,卷门不为它关,问题清单留在「别只信AI」事后处理 |
| 开关粒度 | **单一总开关**(全局),默认开启 |
| 刹车点 | **主线讲完就停**(所有知识点都讲到 = MainLineDone);扩展阅读仍手动 |

## 方案选型

- 方案 A(全循环推进器):整条链换成单步驱动统一回路。心智最一,但重写全部计费/防重/进度模型,回归风险最高。**不选。**
- **方案 B(选定):保留现有静态展开链,只在"当下算不出步数"的接缝加动态再武装。** 复用链的全部优点(重启续跑、会话进度、前台通知、取消、防重),新增面最小。
- 方案 C(只修重试+卷门):达不到"点一次跑到底"。**不选。**

## 设计(方案 B)

### 1. 新阶段 `GenerationStage.ADVANCE`——自动闭环的驱动器

一个低成本的决策 Worker。常态下只查库、不调模型;唯一例外是续卷决策(§5)会当场调一次 `generateNextVolume`。在链尾运行,查库决定下一步,把后续工作用 `beginUniqueWork(..., ExistingWorkPolicy.APPEND, ...)` 挂到**同一条项目唯一链**上,并在其后再挂一个 ADVANCE(自我续订):

```
[知识主干(+自动补漏)] → [讲述路线] → [ADVANCE]
   ADVANCE 查库:
   ├─ 总开关关            → 停(不发通知,用户随时可再点继续)
   ├─ 主线讲完(MainLineDone)→ 发「主线讲完了」结果通知,停   ← 刹车
   ├─ 本卷还有未写章节     → APPEND [章 × N] → [SUMMARY] → [ADVANCE]
   └─ 本卷写完,还有未讲知识点 → (当场规划下一卷,见 §5)→ APPEND [章 × N(新卷)] → [SUMMARY] → [ADVANCE]
```

判定逻辑收进一个可单测的纯函数(`worker` 包,输入 = 当前 plans/nodes/开关状态,输出 = 决策枚举):

```kotlin
internal sealed interface AdvanceDecision {
    data object SwitchOff : AdvanceDecision            // 不追加任何工作
    data class GenerateChapters(val chapterIds: List<String>) : AdvanceDecision
    data class PlanVolumeThenGenerate(val pendingCount: Int) : AdvanceDecision
    data object MainLineDone : AdvanceDecision          // 发通知后停
}
```

章节集合复用 `selectChaptersToGenerate(plans, includeNeedsReview=false)`(`GenerationStage.kt:73-89`)——该函数本就为批量展开设计。

为什么可行且安全:
- **取消不变**:APPEND 仍挂在 `generation-<projectId>` 唯一名下,一次 `cancelUniqueWork` 清掉整条动态链(含还没轮到的 ADVANCE)。
- **防重复扣费不变**:`KEEP` 只作用于用户发起的入口入队(`enqueueChain`,`GenerationEnqueuer.kt:205`);运行中 APPEND 的是「此刻才决定、此前不存在」的工作,不是第二个收费任务。
- **不依赖新 WorkManager API**:2.9.1 无 `ChainingConstraints`,但核验带问题发布走的是 `Result.success`(`PipelineService.kt:2126-2150`),NEEDS_REVIEW 章不会断链;真正失败(重试耗尽)断链后,点「重试」= `enqueueOneTap` 重新进入自动循环,从断点恢复。
- 决策全部现查数据库,与 `FIRST_CHAPTER` 同一思路(`GenerationWorker.kt:129-147`),进程重启天然安全。

### 2. 入队侧改动

- `GenerationEnqueuer.oneTap(...)`:链从「…→ [首章] → [SUMMARY]」改为「…→ [首章] → [SUMMARY] → [ADVANCE]」(总开关关时不挂 ADVANCE,行为与今天完全一致)。`enqueueOneTap` 的语义随之从"生成一章"升级为"跑完主线"。
- 新增 `GenerationEnqueuer.autoContinue(...)`:供「继续」按钮在**已有节点、路线已就绪**时直接挂 `[未写章 × N → SUMMARY → ADVANCE]`(冷启动才需要主干/路线)。
- 进度单元:ADVANCE 自身算 1 个单元;每章仍 `UNITS_PER_CHAPTER`;SUMMARY 文案沿用"已完成 N/M 章"(`GenerationWorker.kt:157-181`),续卷时 M 随 plans 增长如实变大——如实,不虚报。

### 3. 卷门修复(见不到第二卷的直接病根)

`PipelineService.nextVolumeAvailability`(`PipelineService.kt:1574-1592`):

```
旧:本卷任何一章 !isReadable → CurrentVolumeUnfinished(按钮永久消失)
新:本卷仍有「未完成生成」的章(status ∈ {QUEUED, RUNNING, VERIFYING, DRAFT}) → CurrentVolumeUnfinished
   本卷全部章已到终态(PUBLISHED / QUIZ_FAILED / NEEDS_REVIEW / FAILED) → CanContinue / MainLineDone
```

NEEDS_REVIEW / FAILED 章仍计入「需要处理」的 UI 提示(红色卡片与「全部重试」原样保留,`ProjectDetailScreen.kt:1430-1452`),只是不再堵死续卷入口——待复核章正文可读,下一卷开场所需的"上一章结尾状态"取的是**已发布版本**,不受个别待复核章影响(`runChapter` 的 `previousEnding` 逻辑,`PipelineService.kt:1855-1859`)。

失败章(FAILED)在自动链里天然兜住:`selectChaptersToGenerate`(`GenerationStage.kt:73-89`)对它返回 true(不满足 `isReadable`,也不落在 NEEDS_REVIEW 分支),点「继续」即重排;契约 FAILED 的章继续被排除(现状正确——没契约写正文等于凭空发挥)。

### 4. 漏知识点自动补(进自动化)

位置:`KNOWLEDGE_MAP` Worker 的 FULL 模式成功后(审计已在 `PipelineService.kt:512+` 跑完、gap 已落库),若总开关开启:

```kotlin
// PipelineService 新增,复用现有 generateKnowledgeMapPatch(已幂等:同名节点直接 RESOLVED)
suspend fun autoResolveGaps(projectId: String, limit: Int = 10): Int {
    val gaps = knowledgeRepository.getGaps(projectId)
        .filter { it.gapStatus == GapStatus.OPEN && it.actionable }
        .take(limit)
    var done = 0
    for (gap in gaps) {
        // 单条失败不中断:gap 留 OPEN,下次点继续再补;非 actionable 软提醒永不自动关
        if (generateKnowledgeMapPatch(projectId, gap.id).isSuccess) done++
    }
    return done
}
```

- 上限 10 条/批:补一条 = 一次模型调用,批后仍有 OPEN 的在「别只信AI」里手点(或下次自动补)。
- 走现有 `generateKnowledgeMapPatch`,不产生第二套补节点逻辑。
- Worker 进度:每补 1 条上报一格,避免界面长时间静默。

### 5. 自动续卷的模型调用归属

`ADVANCE` 决策 `PlanVolumeThenGenerate` 时,在自身 `doWork` 里直接调 `container.pipeline.generateNextVolume(projectId)`(同步、一次模型调用、append-only 不改已发布章节,`PipelineService.kt:1677-1701`),成功后才 APPEND 新卷章节。它不是独立 stage——续卷决策与执行同属一次 ADVANCE,失败即 ADVANCE 失败(可重试/断链语义统一)。续卷需要 STORY 角色配置:ADVANCE 常态 `requiredRoles` 为空,但走到续卷分支时若缺配置,按永久配置错停链给可读原因(同 `missingRoles`,`GenerationWorker.kt:301-309`),不白烧重试。

### 6. 总开关

- `LearningPrefs` 新增 `generationAutoAdvance: Boolean`,**默认 true**,完全照抄 `spacedReviewEnabled` 模式(`LearningPrefs.kt:23-31`:`MutableStateFlow` 播种 + StateFlow 暴露 + setter 写盘)。
- 注入:`AppContainer` 里以 `() -> Boolean` lambda 传给 `GenerationEnqueuer` 判定与 `PipelineService.autoResolveGaps` 门,与 `spacedReviewEnabled = { learningPrefs.spacedReviewEnabled.value }`(`AppContainer.kt:104`)同款;运行中现读,改设置即生效。
- 全局而非按项目:与 `spacedReviewEnabled` 一致的先例;语义是"你愿意让 AI 自动往下写多少",对整个 App 是同一种信任。
- `SettingsScreen` 「学习方式」段新增一张开关卡(样式抄 `SettingsScreen.kt:155-184` 的间隔复习行):
  - 标题:**自动写到主线讲完**
  - 副标题:开启后,点一次「继续」会自动完成:补齐未写的每一章、自动补上漏掉的知识点、本卷写完自动规划下一卷,直到知识主干全部讲到才停。关闭则回到每步手动确认。
  - 尾注:自动补漏知识点每批最多 10 条;所有自动行为随时可在生成横幅上取消。

### 7. UI 文案与入口微调

- `OneTapCard`(`ProjectDetailScreen.kt:559-617`)副标题按开关联动:开 → "会自动一卷一卷写到主线讲完,可随时取消";关 → 保持现状。
- `NextVolumeCard` 不动:自动链点亮它之前,用户大概率已经不需要它了;手动模式(开关关)下它仍是唯一续卷入口,且卷门修复后不再被待复核堵死。
- `GenerationBanner` 不动:「重试」按钮已经走 `enqueueOneTap`,自动模式下天然就是"从断点恢复整个循环"。

## 错误处理汇总(链在什么情况下停)

| 情形 | 行为 |
|---|---|
| 瞬时故障(网络/超时/5xx) | WorkManager 指数退避自动重试 ≤3 次(`GenerationWorker.kt:188`、`MAX_RETRY_ATTEMPTS=3`) |
| 429 限流 | Router 内部退避已做,不双层重试(`GenerationStage.kt:95-105` 现状,不动) |
| 永久配置错(缺配置/认证) | 立即停链,横幅给可读原因 + 去设置入口(现状) |
| 单章重试耗尽仍失败 | 链停在失败章,通知 PARTIAL;点「继续」→ 自动重排该章并恢复循环 |
| 核验有问题、修复没修干净 | **不停链**:正文带问题发布,状态 NEEDS_REVIEW,卷门放行 |
| 续卷模型调用失败 | ADVANCE 失败 → 退避重试 → 仍失败停链给原因;已发布章节不受影响 |
| 用户取消 | `cancelUniqueWork` 一次清全链(含未轮到的 ADVANCE),现状不变 |
| 总开关中途关闭 | 下一个 ADVANCE 读到即停,不追加;已在链上的当前章写完为止 |

## 测试

1. **纯函数**:`AdvanceDecision` 判定表——开关关 / 有未写章 / 卷终态+有 pending / MainLineDone / FAILED 章是否重排 / 契约 FAILED 章是否排除。
2. **调度(Robolectric + work-testing,已有依赖)**:oneTap 在开/关两态下排出的链形状;ADVANCE 成功 APPEND 后 `getWorkInfosForUniqueWork` 可见新步且 unique 名不变;取消一次清全链。
3. **卷门回归**:存在 NEEDS_REVIEW/FAILED 章时 `nextVolumeAvailability` 不再返回 `CurrentVolumeUnfinished`;仍有 RUNNING 章时仍然返回。
4. **补漏**:`autoResolveGaps` 对 actionable OPEN gap 逐条 RESOLVED、非 actionable 不碰、上限生效、单条失败不中断其余。
5. **e2e 冒烟**(`_claude_e2e/` 已有 mock LLM):mock 一个 2 节点小主干+2 卷剧本,点一次「继续」后断言第二卷章节出现在 plans——正是用户报告的"只见第一卷"的反例。

## 不做的事(边界)

- 不做"扩展阅读卷"的自动续(刹车点 = MainLineDone,已确认)。
- 不改核验/出题内部逻辑(带问题发布、QUIZ_FAILED 不算可读等现状保留)。
- 不加按项目的开关(全局一个,已确认)。
- 不升级 WorkManager(2.9.1 约束下设计已自洽)。
- 不动数据库 schema(零迁移)。
